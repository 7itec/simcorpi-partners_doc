📋 GET /jobs/partners/details/json

Retorna o detalhamento completo dos atendimentos de um dia específico em formato JSON com paginação. O conteúdo é equivalente ao da exportação XLSX, porém entregue como JSON paginado (até 100 atendimentos por página) para consumo por parceiros externos e integrações.

1. Endpoint

GET /jobs/partners/details/json
Propriedade Valor
Autenticação Header x-api-key: <chave>
Paginação Cursor — até 100 atendimentos/página via paginationToken no envelope
Cache 5 minutos
Ordenação startDate + _id ascendentes

2. Query Parameters

Parâmetro Tipo Obrigatório Regra
date string Sim Formato dd/MM/yyyy (ex.: 27/04/2026) — dia exato a consultar
paginationToken string Não Token retornado no envelope da resposta anterior. Omita para obter a primeira página.

3. Paginação

Modelo cursor-based com o mesmo envelope dos endpoints de promptness. Cada requisição retorna até 100 atendimentos distintos (identificados por _id_atendimento).

  • Primeira página: envie apenas date
  • Próximas páginas: envie date + paginationToken da resposta anterior
  • Parar quando isLastPage === true (ou quando paginationToken estiver ausente)

Envelope retornado:

{
  "data":            [ /* linhas dos até 100 atendimentos */ ],
  "count":           450,
  "isLastPage":      false,
  "paginationToken": "CLrnGxoGEICAgIAIGg5..."
}

count: retornado apenas na primeira página (quando paginationToken não é enviado). Representa o total de atendimentos do dia filtrado.
paginationToken: fica na raiz da resposta enquanto houver mais páginas. Não vem mais dentro de cada item de data.
Linhas vs atendimentos: um atendimento com vários passageiros (tripulação) gera mais de uma linha em data, todas com o mesmo _id_atendimento. Por isso data.length pode ser maior que 100, mesmo com no máximo 100 atendimentos por página. Use _id_atendimento (ou id_atendimento) para agrupar, não o tamanho do array.

4. Shape da Resposta (data)

Cada item em data contém os campos de negócio com nomes em português (com acentos e snake_case), idênticos aos cabeçalhos da exportação XLSX equivalente, mais o identificador interno _id_atendimento. Isso facilita comparar os dois formatos e migrar relatórios.

5.3 Erro de autenticação — x-api-key ausente ou inválida

GET /jobs/partners/details/json?date=27/04/2026
# (sem header x-api-key)

Resposta (401):

{ "statusCode": 401, "message": "Unauthorized" }

5.4 Erro de parâmetro — date ausente ou inválido

Resposta (400):

{ "statusCode": 400, "message": "A data precisa estar no formato dd/mm/yyyy" }

6. Erros Comuns

HTTP Cenário Mensagem
400 date ausente Mensagem do validador (@IsNotEmptyPTBR)
400 date em formato errado A data precisa estar no formato dd/mm/yyyy
401 x-api-key ausente ou inválida Unauthorized
500 Erro interno Mensagem variável

7. Cuidados Operacionais

  • Itere pelo paginationToken do envelope: para dias com muitos atendimentos, consuma as páginas em sequência usando o token da raiz da resposta. Pare quando isLastPage === true (ou quando paginationToken não vier). Não use data.length < 100 como critério de parada — o array pode ter mais de 100 linhas por causa de múltiplos passageiros no mesmo atendimento.
  • Agrupe por atendimento quando necessário: se a integração precisa de um registro por atendimento, agrupe as linhas de data por _id_atendimento.
  • Cache de 5 minutos: chamadas repetidas na mesma janela retornam o cache. Evite iterar as páginas com intervalo maior que 5 minutos para manter consistência na mesma extração.
  • Escopo por parceiro: a x-api-key define o recorte de dados retornado. Chaves diferentes podem retornar conjuntos distintos para o mesmo date.
